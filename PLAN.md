# План: распознавание номенклатуры и клиента

Состояние на 2026-09-26. Этап — **интеграция**: разбор выдаёт черновик заказа менеджеру,
автоматической отправки в 1С нет.

## Где мы сейчас

Офлайн-оценка (`experiments/voice-order-20260924/evaluate_offline.py`, 20 записей, 92 позиции):

| | Позиций | Авто и верно | Авто и **неверно** | На проверку |
|---|---:|---:|---:|---:|
| sample10 (на нём настраивали правила) | 52 | 37 | 1 | 13 |
| holdout10 (честная цифра) | 40 | 14 | 0 | 26 |

- Номенклатура: правила без облака (`order_pipeline.py`), строка подтверждается только если
  прошли все проверки. Выборка мала, эталон составлен по тексту SpeechKit, а не по аудио.
- Клиент (`client_matching.py`): работает, но **точность не измерена** — в эталоне клиентов нет.
- Около половины строк на проверке — настоящая неоднозначность каталога (газ / в/у, начинки).

## Текущий этап

1. **Эталон побольше и метрика клиента.** 100–200 записей через `run_batch.py`, в разметку
   добавить клиента; `evaluate_offline.py` считает клиента: верно / неверно / на проверку.
   Часть записей (≥30) размечать по прослушиванию аудио, а не по тексту распознавания.
   Условие для автоотправки в 1С — не больше 0,5% неверных автоподтверждений на 500+ позициях.
2. **Подсказки распознаванию из справочника.** SpeechKit: список фраз (названия товаров, фамилии
   клиентов филиала). GigaAM: исправление слов по словарю справочника после распознавания.
3. **Выгрузка в 1С** подтверждённых строк; строки на проверке не уходят.

Дубли в справочниках 1С (одинаковые названия с разными ID) **не исправляем**: это реальная
ситуация у клиентов. Мы предупреждаем (`catalog_validation.py`) и отправляем такие строки на проверку.

## Отложено: идеи верные, но не на этапе интеграции

Предлагать при обсуждении улучшений, не реализовывать сейчас.

- **Исправления менеджера.** Выбор товара из кандидатов и правка количества прямо в строке заказа,
  кнопка «Подтвердить заказ», сохранение в `orders` / `order_items` вместе со сказанным
  (`spoken_name`). Пара «сказано → выбранный товар» у клиента становится сигналом для
  автоподтверждения и одновременно разметкой для оценки. Сейчас таблицы есть, но разбор в них
  не пишет; обучение есть только для клиента (`ClientTeach`).
- **История заказов клиента.** Когда подходят несколько товаров, различающихся несказанным словом,
  выбирать тот, что клиент стабильно брал («как в прошлый раз»). Сюда же — правила по умолчанию
  от менеджера филиала («Венский без уточнения = п/к»). Закрывает около половины оставшихся проверок.
- **Проверка клиента по ассортименту.** Если найденный клиент никогда не брал названные товары,
  а второй кандидат берёт их постоянно — понижать уверенность или отправлять на проверку. В обратную
  сторону: состав заказа подсказывает клиента, когда назван только адрес.
- **Вероятностная уверенность строки** (логистическая регрессия / бустинг на признаках, которые
  уже считаются: `match_quality`, число подходящих, отрыв от второго, фасовка, история) вместо
  ручных порогов. Требует разметки из исправлений менеджера.
- **LLM как арбитр** только для строк, ушедших на проверку; её выбор проходит через `decide`.
