# Разбор голосовых заказов: проверка на 20 записях, 24.09.2026

## Итог

Прежний разбор (весь справочник в YandexGPT одним запросом) на 20 случайных записях из `local/`
автоматически подтвердил **12 из 92 позиций правильно и 18 неправильно**: чужой товар
(«рулет индейка запеченный 9» → «Крыло индейки», «зельц борский» → «Колбаса Гурман»),
перепутанные количества у двух зельцев, «кило восемьсот» → 800 г, товар «НЕ БРАТЬ».
Неправильная строка, помеченная как готовая, хуже строки на проверку: менеджер её не заметит.

Новый разбор (`backend/order_pipeline.py`, без облачных вызовов) на тех же 20 записях:
**51 позиция подтверждена правильно, 1 спорно** (см. ниже), остальное — на проверку с понятной причиной.

прежде чем включать автоотправку в 1С, прогоните 50–100 записей через `run_batch.py` и разметьте.

## Что показала проверка

1. **Количества надёжнее разбирать кодом, чем моделью.** «кило двести», «два шестьсот», «два и семь»,
   «ноль восемь», «полтора», «три целых две десятых» — фиксированные формы речи.
   `spoken_quantity.py` разбирает их одинаково всегда; количество, которое модель вернула,
   но которого нет в цитате, больше не проходит.
2. **Позицию режут произнесённые количества, а не паузы.** Паузы SpeechKit часто посреди позиции
   («рулет индейка запеченный / девять»). `order_segmenter.py` режет по количествам, отбрасывает
   адрес/клиента в начале, привязывает «комментарий … только большие» к тому товару, который назван
   в комментарии, а не к последнему.
3. **Выбор товара без модели оказался не хуже модели.** Проверено на 10 записях настройки: те же
   кандидаты и проверки, но выбор делает YandexGPT — 26 верных автоподтверждений против 36 без модели.
   Модель на выборе из 8 кандидатов ошибалась (гусиный «Охотник», порция 0.300 вместо весового рулета, колбаски
   вместо купат) и почти всегда писал «есть сомнения». Лексический поиск + проверки дали больше
   правильных автоподтверждений. Оговорка: модель вызывалась через существующий `/api/process-order`,
   где её системный промпт конфликтовал с задачей, так что это не окончательный приговор LLM.
4. **Проверки, которые не дают угадывать:**
   - каждое сказанное слово должно найтись в названии (с учётом падежей, «ск» = с/к, «куриный» = ЦБ,
     «утиный» = УТКИ); незнакомое слово («северолатвенский») — проверка;
   - если подходят два товара, различающиеся тем, чего клиент не сказал (газ / в/у, «Охотник» гусиный /
     п/к, купаты с сыром / с травами) — проверка с перечислением вариантов;
   - порция/половинка/0.300/штучный выбирается, только если клиент это сказал; «весовой» — наоборот;
   - «НЕ БРАТЬ» и услуги (транспорт, 1С, аренда) не предлагаются;
   - единица: сказанная, иначе из справочника; «шт» при товаре в кг — проверка «нужен пересчёт».
5. **Справочник.** Два одинаковых «Сосиски "Фермерские" из мяса индейки» с разными ID — всегда
   уйдут на проверку, пока дубль не убрать в 1С.

## Что осталось на проверку (39 строк) и что даст ещё конверсию

- Реальная неоднозначность каталога (газ/без газа, в/у/без, разновидности купат, пельменей) —
  около половины. Даст рост: **правило по умолчанию от менеджера** («Венский без уточнения = п/к»)
  или история заказов клиента (что он брал в прошлый раз).
- Ошибки распознавания названий («северолатвенский», «закарейка», «гуска», «леверное эно»).
  Варианты произношения из `voice_dictionary` теперь заменяются на актуальное название товара
  перед разбором. Числовые артикулы и коды в такую замену не попадают.
- Позиции без количества (обрезанное сообщение) и продолжения заказа в следующем голосовом
  («два с половиной килограмма» в начале файла). Даст рост: склейка подряд идущих голосовых
  одного клиента в один заказ.
- Клиент/адрес в начале сообщения сейчас просто отбрасывается. Для заказа в 1С его нужно
  сопоставлять со справочником контрагентов.

## Локальное распознавание GigaAM-v3 против SpeechKit (те же 20 записей)

GigaAM-v3 (`v3_rnnt`, 220 млн параметров, MIT) запускается в контейнере backend на процессоре,
аудио не покидает компьютер. Разбор заказа одинаковый (правила выше), эталон тот же.

| 92 позиции, 20 записей | SpeechKit + правила | GigaAM + правила |
|---|---:|---:|
| Количество верное | 89 | 86 |
| Авто и верно | 51 | 50 |
| Авто и неверно по эталону | 1 | 3* |
| Время на 20 файлов (≈4,7 мин аудио) | ~25–35 с на файл, облако | 6 мин всего, CPU, первый запуск +2 мин на загрузку весов |
| Стоимость | платно за каждую минуту | 0 |

\* Эталон составлен по тексту SpeechKit, поэтому там, где GigaAM услышала больше, она считается
ошибкой. Два из трёх случаев, скорее всего, ошибки эталона: «сосиски вознесенские **один**»
(SpeechKit не услышал «один») и «**сервелат венский** газ» (SpeechKit: «северолатвенский»,
такого товара нет). Третий — общий для обоих «рулет филейный 1,6 кг». Сообщение-исправление
(«написали 4, просят исправить на шесть») после проверки отправляется менеджеру целиком.

GigaAM чаще точнее в названиях: «рулет кд» (SpeechKit: «рулетка д»), «корейка хмельницкая»
(«закарейка»), «зельц», «студень», «буженаль»; и не теряет короткие количества в конце фразы.
Части длинного аудио перекрываются на 0,8 секунды; повторившиеся слова на стыке удаляются.
Размер части и перекрытия настраиваются через `GIGAAM_CHUNK_SEC` и `GIGAAM_OVERLAP_SEC`.
Вывод: по качеству заказа — не хуже SpeechKit, бесплатно и без передачи аудио. Чтобы уверенно
выбрать, прослушайте 3–5 спорных записей (список выше) и разметьте ещё 30–50 через `run_batch.py`.

## Как включено

`server.py`: разбор идёт через `order_pipeline.parse_order`, без облака и без API-ключа;
без выбранного сотрудника — ошибка «Выберите сотрудника» (YandexGPT не вызывается).
`ORDER_PARSER=llm` возвращает прежний платный разбор через YandexGPT.
Распознавание: переключатель в интерфейсе (SpeechKit / GigaAM) или `STT_ENGINE` по умолчанию.
В интерфейсе у строки показываются «Сказано: …» и «Комментарий: …».
