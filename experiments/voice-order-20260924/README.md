# Разбор голосовых заказов: проверка на 20 записях, 24.09.2026

## Итог

Прежний разбор (весь справочник в YandexGPT одним запросом) на 20 случайных записях из `local/`
автоматически подтвердил **12 из 92 позиций правильно и 18 неправильно**: чужой товар
(«рулет индейка запеченный 9» → «Крыло индейки», «зельц борский» → «Колбаса Гурман»),
перепутанные количества у двух зельцев, «кило восемьсот» → 800 г, товар «НЕ БРАТЬ».
Неправильная строка, помеченная как готовая, хуже строки на проверку: менеджер её не заметит.

Новый разбор (`backend/order_pipeline.py`, без облачных вызовов) на тех же 20 записях:
**51 позиция подтверждена правильно, 1 спорно** (см. ниже), остальное — на проверку с понятной причиной.

## Что показала проверка

1. **Количества надёжнее разбирать кодом, чем моделью.** «кило двести», «два шестьсот», «два и семь»,
   «ноль восемь», «полтора», «три целых две десятых» — фиксированные формы речи.
   `spoken_quantity.py` разбирает их одинаково всегда; количество, которое модель вернула,
   но которого нет в цитате, больше не проходит.
2. **Позицию режут произнесённые количества, а не паузы.** Паузы SpeechKit часто посреди позиции
   («рулет индейка запеченный / девять»). `order_segmenter.py` режет по количествам, отбрасывает
   адрес/клиента в начале, привязывает «комментарий … только большие» к тому товару, который назван
   в комментарии, а не к последнему.
3. **Выбор товара без модели оказался не хуже модели.** Проверено на 10 записях настройки: те же
   кандидаты и проверки, но выбор делает YandexGPT — 26 верных автоподтверждений против 36 без модели.
   Модель на выборе из 8 кандидатов ошибалась (гусиный «Охотник», порция 0.300 вместо весового рулета, колбаски
   вместо купат) и почти всегда писал «есть сомнения». Лексический поиск + проверки дали больше
   правильных автоподтверждений. Оговорка: модель вызывалась через существующий `/api/process-order`,
   где её системный промпт конфликтовал с задачей, так что это не окончательный приговор LLM.
4. **Проверки, которые не дают угадывать:**
   - каждое сказанное слово должно найтись в названии (с учётом падежей, «ск» = с/к, «куриный» = ЦБ,
     «утиный» = УТКИ); незнакомое слово («северолатвенский») — проверка;
   - если подходят два товара, различающиеся тем, чего клиент не сказал (газ / в/у, «Охотник» гусиный /
     п/к, купаты с сыром / с травами) — проверка с перечислением вариантов;
   - порция/половинка/0.300/штучный выбирается, только если клиент это сказал; «весовой» — наоборот;
   - «НЕ БРАТЬ» и услуги (транспорт, 1С, аренда) не предлагаются;
   - единица: сказанная, иначе из справочника; «шт» при товаре в кг — проверка «нужен пересчёт».
5. **Справочник.** Два одинаковых «Сосиски "Фермерские" из мяса индейки» с разными ID — всегда
   уйдут на проверку, пока дубль не убрать в 1С.

## Что осталось на проверку (39 строк) и что даст ещё конверсию

- Реальная неоднозначность каталога (газ/без газа, в/у/без, разновидности купат, пельменей) —
  около половины. Даст рост: **правило по умолчанию от менеджера** («Венский без уточнения = п/к»)
  или история заказов клиента (что он брал в прошлый раз).
- Ошибки распознавания названий («северолатвенский», «закарейка», «гуска», «леверное эно»).
  Варианты произношения из `voice_dictionary` теперь заменяются на актуальное название товара
  перед разбором. Числовые артикулы и коды в такую замену не попадают.
- Позиции без количества (обрезанное сообщение) и продолжения заказа в следующем голосовом
  («два с половиной килограмма» в начале файла). Даст рост: склейка подряд идущих голосовых
  одного клиента в один заказ.
- Клиент/адрес в начале сообщения сейчас просто отбрасывается. Для заказа в 1С его нужно
  сопоставлять со справочником контрагентов.

## Локальное распознавание GigaAM-v3 против SpeechKit (те же 20 записей)

GigaAM-v3 (`v3_rnnt`, 220 млн параметров, MIT) запускается в контейнере backend на процессоре,
аудио не покидает компьютер. Разбор заказа одинаковый (правила выше), эталон тот же.

| 92 позиции, 20 записей | SpeechKit + правила | GigaAM + правила |
|---|---:|---:|
| Количество верное | 89 | 86 |
| Авто и верно | 51 | 50 |
| Авто и неверно по эталону | 1 | 3* |
| Время на 20 файлов (≈4,7 мин аудио) | ~25–35 с на файл, облако | 6 мин всего, CPU, первый запуск +2 мин на загрузку весов |
| Стоимость | платно за каждую минуту | 0 |

\* Эталон составлен по тексту SpeechKit, поэтому там, где GigaAM услышала больше, она считается
ошибкой. Два из трёх случаев, скорее всего, ошибки эталона: «сосиски вознесенские **один**»
(SpeechKit не услышал «один») и «**сервелат венский** газ» (SpeechKit: «северолатвенский»,
такого товара нет). Третий — общий для обоих «рулет филейный 1,6 кг». Сообщение-исправление
(«написали 4, просят исправить на шесть») после проверки отправляется менеджеру целиком.

GigaAM чаще точнее в названиях: «рулет кд» (SpeechKit: «рулетка д»), «корейка хмельницкая»
(«закарейка»), «зельц», «студень», «буженаль»; и не теряет короткие количества в конце фразы.
Части длинного аудио перекрываются на 0,8 секунды; повторившиеся слова на стыке удаляются.
Размер части и перекрытия настраиваются через `GIGAAM_CHUNK_SEC` и `GIGAAM_OVERLAP_SEC`.
Вывод: по качеству заказа — не хуже SpeechKit, бесплатно и без передачи аудио. Чтобы уверенно
выбрать, прослушайте 3–5 спорных записей (список выше) и разметьте ещё 30–50 через `run_batch.py`.

## Как включено

`server.py`: разбор идёт через `order_pipeline.parse_order`, без облака и без API-ключа;
без выбранного филиала — ошибка «Выберите филиал» (YandexGPT не вызывается).
«Сотрудник» в интерфейсе теперь называется «Филиал» (руководитель филиала); в БД и API
по-прежнему `employees`.
`ORDER_PARSER=llm` возвращает прежний платный разбор через YandexGPT.
Распознавание: переключатель в интерфейсе (SpeechKit / GigaAM) или `STT_ENGINE` по умолчанию.
В интерфейсе у строки показываются «Сказано: …» и «Комментарий: …».

### Опции филиала (вкладка «Настройки разбора», все отключаемые)

Хранятся в `employees.order_settings` (JSON, `backend/order_settings.py`):

- **Реалистичность количества.** Проверяется только там, где задан максимум: у позиции
  номенклатуры («Реалистичный максимум в заказе», `nomenclature.max_quantity`, в её единице хранения)
  или общий максимум филиала для кг / шт / уп (по умолчанию не задан). Без максимума большое
  количество считается нормальным заказом и на проверку не уходит.
  - **Граммы.** «Сосиски пятьсот» при максимуме 5 кг, если единица не сказана, — это 500 г:
    количество становится 0.5 кг с пометкой (`auto_note`), без отправки на проверку.
  - На проверку уходит только то, что больше максимума и граммами быть не может
    («пятьсот килограмм», «шесть» при максимуме 5 кг).
  - Проверка справочника показывает, у скольких позиций максимум не задан.
- **Фасовка из названия.** «Зельц говяжий двести пятьдесят» при товарах «Зельц 250 гр» и
  «Зельц 2500 гр»: число 250 — фасовка из названия. Оно выбирает товар «Зельц 250 гр»,
  а количество остаётся пустым: его нужно уточнить.
- **Поправки в речи.** «Два кило, точнее три», «пять, нет, семь», «то есть», «вернее» меняют
  количество предыдущей строки. Если после поправки назван другой товар, обе строки уходят на проверку.
- **Клиент** (`client_matching.py`). Ищется в начале сообщения, до первого товара (если там нет —
  в остальном тексте вне названий товаров), по справочнику клиентов филиала и словарю (категория `client`).
  Из имени 1С «Ногуманова Л.Л.(г.Лениногорск, ул.Степная,1)» / «ИП Ногуманова Люция Людвиговна» берутся
  ключ (фамилия; у организации — название без ООО/ИП) и подтверждающие слова (имя, отчество, город, улица).
  Падежи и типичные ошибки распознавания учитываются («нуреевым» = Нурыев).
  Уверенность: сокращение из словаря 1.0; ключ 0.85, каждое подтверждающее слово +0.05; только город
  и улица — 0.35–0.45 (подсказка). Подтверждается при ≥0.85, если следующий кандидат слабее хотя бы
  на 0.05: две одинаковые фамилии уходят на проверку, названный город решает спор. Коды 1С и одно
  слово адреса/имени клиентом не считаются. Конфликты сокращений видны во вкладке «Клиенты» филиала
  и в «Проверке справочника»; `GET /api/employees/<id>/clients` возвращает у каждого клиента `voice`
  (как его можно назвать) и общий список `voice_conflicts`.
- **Склейка голосовых** (`order_merging.py`, `POST /api/process-orders`). Сообщения сортируются по
  времени записи из имени файла («2026-08-23 21-37-42.mp3», иначе время файла). Следующее
  сообщение продолжает заказ, если это тот же клиент, если оно начинается с количества, если
  предыдущее закончилось названием без количества или если между ними не больше окна (15 мин)
  и клиент не назван. Другой клиент или большой перерыв начинают новый заказ. Причина каждой
  склейки показывается в результате.

### Мера при конфликте товаров

Если под сказанное подходят несколько товаров, у каждого считается точность совпадения слов
(`order_pipeline.match_quality`: точное слово, сокращение или падеж — 1, иначе сходство букв).
Оставляются только товары в пределах 0.05 от лучшего: «сервел отвенский газ» → «Сервелат Венский газ».
Товары, различающиеся несказанным словом (газ / в/у, начинка купат), по-прежнему уходят на проверку.
На 20 записях: sample 37 верных автоподтверждений (было 36), holdout 14 / 0 неверных, новых ошибок нет.

### Полустандарт диктовки (пилот)

«Клиент. Товар, сколько. Дальше — товар, сколько. … Комментарий … Всё.» — не обязателен:
свободная речь разбирается как раньше, формат только помогает.
- «дальше / далее / следующее / потом / затем» закрывают позицию: «бочок индейки, дальше краковская три»
  даёт две строки (у первой «Уточните количество»), а не одну «бочок индейки краковская 3»;
  разделитель также заканчивает комментарий;
- «комментарий бочок крупный» уходит к позиции «бочок», а не к последней;
- первый товар после клиента находится и при ошибке распознавания («егерская» = «Егерьская»,
  сходство ≥ 0.88, от 6 букв; улица «Тукая» ≠ «тушка»).

Защита от ухудшения: на 35 реальных расшифровках (20 SpeechKit + 15 GigaAM) разбор свободной речи
совпадает с версией до этих правок строка в строку; `check_format.py` переписывает каждый заказ
в формат и требует не меньше автоподтверждений (сейчас 78 против 77, хуже — 0).

### API и переключение

- `GET /api/engines` — готовность вариантов распознавания (`gigaam`, `speechkit`) и разбора (`rules`, `llm`)
  и значения по умолчанию сервера (`STT_ENGINE`, по умолчанию `gigaam`; `ORDER_PARSER`, по умолчанию `rules`).
- `POST /api/recognize` (`engine`, `employee_id`, `process_llm`, `parser`) — всегда возвращает `client`,
  если выбран филиал, даже без разбора заказа.
- `POST /api/process-order`, `POST /api/process-orders` принимают `parser: rules|llm`; при `llm` позиции
  разбирает YandexGPT, а клиент и склейка голосовых остаются локальными.
- `POST /api/detect-client` `{employee_id, text}` → `{client}`.
- `POST /api/yandex-cloud/test-connection` `{service: speechkit|yandexgpt}` — проверка каждого сервиса отдельно.
- SpeechKit: аудио удаляется из бакета после распознавания; ошибка опроса операции (401/403)
  прерывает ожидание сразу, а не через час.

### Повторный импорт без дублей

Импорт номенклатуры и клиентов (`catalog_sync.py`) сопоставляет строки файла с уже загруженными:
по коду 1С, затем по артикулу с названием, затем по названию. Найденная позиция обновляется на месте:
ID, лимит, варианты произношения и прошлые заказы сохраняются. Позиции, которых нет в файле,
скрываются (`import_status='removed'`), а не удаляются; при следующем импорте они возвращаются.
Дубли от прежних импортов при повторном импорте скрываются.

### Проверка справочника заранее

`GET /api/employees/<id>/nomenclature/validation` (`catalog_validation.py`) находит позиции,
которые голосом не различить: одинаковые названия с разными ID (ошибка), названия, отличающиеся
только числами (фасовка), одинаковые артикулы и коды, вариант произношения у нескольких позиций,
одинаковые клиенты, позиции вне разбора. Результат виден после импорта, во вкладке «Номенклатура»
и на экране загрузки (ошибки), до распознавания заказа.
