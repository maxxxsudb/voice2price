# Сравнение обработки голосовых заказов — 24.09.2026

## Вывод

Лучший из проверенных вариантов для дальнейшей разработки: **два этапа с лексическим RAG** — выделение позиций → поиск восьми кандидатов по названиям → отдельный выбор товара → проверки в коде. Гибрид с эмбеддингами не улучшил качество на этих двух тестовых записях и требует дополнительного индекса/запросов. Это не доказательство бесполезности эмбеддингов на других заказах.

В рабочий разбор новый вариант **не включён**: в независимом тесте он неправильно присоединяет комментарий к товару. Основная ветка не должна получать эксперимент как готовое решение. Ветка содержит подготовку одного канала, предыдущие исправления интерфейса/API, эксперимент, тесты и результаты.

## Аудио

Во всех четырёх использованных MP3 каналы побитово одинаковы после декодирования. В backend теперь выбирается канал 1, без смешивания, и передаётся SpeechKit как PCM16 mono 16 кГц. Исходный MP3 не меняется, локальный временный PCM удаляется. Для будущего аудио с разными собеседниками на разных каналах такой режим неприменим без отдельного выбора канала.

## Методы

1. **Direct:** один запрос YandexGPT со всеми 317 позициями каталога.
2. **Lexical:** один запрос извлечения позиций, поиск TF-IDF по символьным триграммам + нечёткое сходство слов, top-8; отдельный запрос выбора кандидата для каждой позиции.
3. **Hybrid:** те же извлечение/проверки, объединение лексического и семантического ранжирования через reciprocal rank fusion (k=20), top-8. Эмбеддинги каталога text-search-doc, запросов text-search-query. [Документация Яндекса](https://aistudio.yandex.ru/en/docs/ai-studio/operations/embeddings/search).

У всех одинаковые модель yandexgpt, temperature=0 и проверки: номер должен соответствовать названию; несколько подходящих вариантов требуют уточнения; явно названная единица проверяется по цитате, иначе единица берётся из однозначного товара каталога. Прайс/машина/маршрут исключаются из товарных строк. Никаких новых алиасов по тестам не добавлялось.

## Результат независимого теста

| Показатель | Весь каталог | Лексический RAG | Гибридный RAG |
|---|---:|---:|---:|
| Найдено позиций / ожидается | 9/9 | 9/9 | 9/9 |
| Правильные числовые количества | 9/9 | 9/9 | 9/9 |
| Правильно подтверждено SKU | 3/9 | 5/9 | 5/9 |
| Неправильно подтверждено SKU | 0 | 0 | 0 |
| Отправлено на уточнение | 6 | 4 | 4 |
| Нужный SKU присутствует среди кандидатов | 9/9 (весь каталог) | 9/9 | 9/9 |
| Нужный комментарий у нужного товара | 0/1 | 0/1 | 0/1 |
| Комментарий ошибочно у другого товара | 0 | 1 | 1 |
| Входные токены LLM | 20 347 | 5 936 | 5 906 |
| Выходные токены LLM | 1 129 | 1 239 | 1 239 |

5/9 — это правильные **SKU**, не пять полностью безошибочных строк: одна из этих строк содержит чужой комментарий. Стоимость эмбеддингов в таблицу токенов LLM не включена. Извлечение позиций было общим и закэшированным для двух RAG-методов, его токены включены в каждый метод для честного сравнения затрат отдельного запуска. Времена в сырых файлах зависят от кэша и параллельных запросов; по ним нельзя сравнивать полную задержку. Каждый вариант запускался на тесте один раз.

## Ошибки, которые не подгонялись на тестах

- «Буженина Бон-Аппетит ... весовая 0.6»: правильное количество, но слишком строгая проверка неоднозначности не учитывает атрибут «весовая» и требует ручного выбора. Это избыточное уточнение.
- «Рулет индейка запеченный 0.8» и «рулет ЦБ ... в вакууме 2.6»: количество сохранено, SKU остаётся неопределённым. Проверка упаковки/фасовки избыточно консервативна.
- «Сервелат ивенский 3»: нет уверенного выбора. В каталоге есть два «Венских» с разной упаковкой, поэтому уточнение уместно.
- Комментарий «рулеты из индейки только большие» оба двухэтапных варианта прикрепили к **утиному** рулету. Direct потерял комментарий. Это блокирующая ошибка для автоматического заказа, даже при правильных SKU и количествах.

## Дальнейшая работа

Исправлять присоединение комментариев и проверку явных атрибутов уже на новой итерации. Эти два теста после просмотра становятся известными примерами и больше не являются независимыми. Для следующей проверки можно использовать оставшийся резервный файл и новые записи. Не заявлять универсальную точность по двум коротким тестам. Увеличить долю автоподтверждения только после корректной обработки комментариев.

## Воспроизведение

- Python: docker compose exec -T backend python -m unittest discover -s /app -p 'test_*.py' -v
- UI: docker compose exec -T frontend node --test tests/recognition.test.mjs
- TypeScript/build: docker compose exec -T frontend npm run typecheck; docker compose exec -T frontend npm run build
- Пересчёт отчётных метрик без облачных запросов: python experiments/benchmark-20260923/evaluate.py
- Для новых облачных прогонов runner.py копируется в /app/benchmark_runner.py контейнера backend; catalog.json и транскрипты — в /tmp/voice-benchmark. Команды: python /app/benchmark_runner.py index, затем python /app/benchmark_runner.py dev1 lexical (direct/hybrid). Скрипт использует серверные настройки, ключи в результатах не сохраняются. Для другого эксперимента нужен отдельный каталог/метки кэша.

Исходные MP3, ключи и кэш эмбеддингов в Git не добавлены. results/ содержит расшифровки, каталог и модельные ответы для аудита. Эти коммерческие данные были предоставлены пользователем для данного эксперимента.
